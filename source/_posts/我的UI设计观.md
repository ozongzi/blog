要设计好的 UI，首先要明白用户喜欢什么，讨厌什么。

<!--more-->

# 反馈

用户喜欢反馈。

点击一个按钮，如果没有反应，用户会再点一下，甚至连点好几下。因为在得到反馈之前，用户无法确认自己的操作到底有没有被系统接收——他敲下去的这个动作，仿佛掉进了虚空。

所以如果你在用户点完按钮之后立刻转去处理任务，那就错了——**处理的速度永远没有反馈的速度重要**。哪怕真正的结果要 3 秒后才出来，按钮也应该在 100ms 内先给出一个「我收到了」的回应:凹陷、变色、涟漪、加载圈，任何东西都行。反馈的作用不是告诉用户「做完了」，而是告诉用户「你的操作是有效的」。这两件事必须解耦——确认接收要快，交付结果可以慢。

反馈的结果不能只有一种。Jessie Schell 在《The Art of Game Design》中强调任意操作都应该同时获得两种以上的反馈，如旋转，抖动，变色，声音，震动……一个多汁的系统可以让人心情愉悦，注意力集中（人类对动的东西比较敏感）。而这就是 UI 存在的意义。 

# 因果

用户喜欢清晰的逻辑。清晰的逻辑有助于用户理解你的模式，而且用户本来能理解你的模式的时候，因果性就更加重要了。

点击一个按钮，屏幕上突然弹出一个窗口，这个设计就是失败的，因为用户不知道这个窗口是从哪里来的。也许用户可以通过思考来判断。但是对于设计 UI 的人来说，如果本身能表达的逻辑却需要用户的思考，那就是设计本身的失败。
一种成功的设计是:点击按钮后，按钮开始生长，逐渐长成一个窗口。这样用户能清楚地感知到因果的连续——「这个窗口是**因为我点了这个按钮**才打开的」。

另一个例子。玩家拖动改变自己的装备。当玩家改变自己的装备的时候，他关注的并不是装备本身，而是装备影响了哪些属性。如果玩家改变装备时，这些数值只是 「静默」 地改变了，那么这个UI就是失败的。正确的设计应该是「吵闹」的，玩家装备放下的那一瞬间，相关的数字开始跳动，因果由此显现。

系统软件也是如此。图书馆管理系统删除一本书的时候，不是 alert('') 这本书被多少人借。什么书在什么地方，什么书被借走了，这些应该清晰地显示在界面上（哪怕仅仅只是一个点或被包含在省略号内）。当管理员想要删除一本书，这些被借走的实例应该跳出来，主动的提醒比需要用户「理解你的报错」更加的高效。

系统设置里面改变一个配色主题，场上的所有配色应该马上开始过渡，而不是要求重启电脑——重启是最糟糕的反馈途径。

# 连续

用户喜欢连续:连续的动画，连续的反馈，连续的因果。同时，连续也是表示因果性最为高效的方式。

这里的「连续」最好不只是数学意义上的连续，而是 $C^2$ 的光滑。比如用低通滤波，至少要串三级——这是电影的标准，用在代码上并不夸张，对程序员来说也不过是几行代码的事。为什么是 $C^2$?因为人眼对速度(一阶)和加速度(二阶)的突变都很敏感。位置连续但速度突变，动画会「顿」一下;速度连续但加速度突变，动画会有种说不出的廉价感。只有加速度也连续了，运动才真正「像真的」。

同理:一个待办列表，应该是输入框滑动到列表顶部，其余项依次让出位置;一个 IM(或 AI Chat App)，用户输入一句话点击发送后，输入框应该形变成消息气泡。

总而言之，不允许存在孤立的因果——任何因果都必须通过动画表达出来。

也许你会问:如果这个因果关系「只可意会，不可言传」怎么办?那恰恰说明你的设计失败了。设计的核心，就是通过间接手段让用户「意会」。

> PS:传输理论里有一个测度叫 WFR(Wasserstein-Fisher-Rao)，即移动-生灭测度。上面的观点可以表述为:UI 需要在 WFR 测度上连续。移动对应元素的位移，生灭对应元素的出现与消失——一个好的 UI 里，没有东西是凭空出现或凭空消失的，它们要么从别处移动过来，要么从某个源头生长出来。

# 信息密度

信息密度是 UI 设计中的一个重要概念。但用户真正在意的，不是信息量与屏幕空间的比值，而是**第一眼**看到你的 UI 时能获取到多少信息——我们追求的是 first glance 时的信息密度。

如果一个监控界面塞满了图表却没有重点，那么这个意义上的信息密度就是 0，和图书管理系统查出一大堆 csv 没有区别。屏幕上的信息量很大，但用户第一眼什么都抓不住，得逐个去读、去比对，信息传递的效率反而趋近于零。

这方面做得最好的是游戏，比如王者荣耀。它的战斗界面信息量惊人:双方血条、技能 CD、装备栏、小地图上的敌我动向、金币经验、buff 状态……但玩家在 0.5 秒内就能抓住当前最要紧的那几个。靠的是分层——颜色、大小、位置、动效把信息按重要度排了序。血量告急时屏幕会闪红，大招好了图标会亮起。它没有降低信息量，而是让最重要的信息「自己跳出来」，把选择的成本从用户身上挪走了。这才是 first glance 信息密度的本质:不是塞得少，而是排得好。

# 新奇度

哪怕做到了以上所有，对于真正好的 UI 来说，还是不够的。好的 UI 必须可以把玩。一个一切都确定，所有变化都是 $lowpass^3$ 的变化的东西是舒服而无趣的。UI还需要不确定性。

这里的不确定性并不是说点击按钮然后发生的事情不确定——那会破坏心流体验。这里所说的是未知与不可掌控感。当用户 hover 到一个按钮的时候，按钮可以弹跳，可以抗拒。服务器负载不是一个百分数，而是一个逐渐红温的机器。当用户用了365天UI，仍然能在第366天打开这个仪表板的时候感到愉悦，此时这个UI才是真正成功了。

# 专业软件的错误

上面这些道理，消费级软件早就烂熟于心。真正的重灾区是所谓的「专业软件」和「工业软件」——那些工控上位机、EDA 工具、示波器面板、企业 ERP、各种行业内部系统。

它们几乎违反了前面说的每一条。

1. 没有反馈。 点一个按钮，进度条卡在那里一动不动，你不知道它是在算，还是已经卡死了。于是你只能干等，或者赌一把点第二下——然后触发一个更糟的状态。

2. 没有连续。 弹窗凭空炸出来，又凭空消失;切换页面是硬切，没有任何过渡;数据刷新是整个表格「啪」地重画一遍，你上一秒在看的那一行瞬间不知道去哪了。所有因果都是孤立的，你得靠自己在脑子里把它们连起来。

3. 没有 first glance 信息密度。 一屏塞进两百个控件，每个都一样大、一样灰、一样重，没有任何主次。真正要紧的那个报警，和一个八百年不点的配置项，长得一模一样。信息量拉满，信息密度归零。

这些软件的辩护通常是:「我们的用户是专业人士，他们受过训练，不需要那些花哨的东西。」

这是傲慢，也是偷懒。

用户「受过训练」不等于「不需要好设计」，只等于「被迫用肌肉记忆去背下你的烂设计」。一个熟练的操作员能在你的界面上飞快操作，靠的不是界面好，而是他花了三个月把每个按钮的位置和每个弹窗的时机都硬记了下来——他是在用人的适应能力，替你的设计还债。而这笔债，每一个新人入职时都要重新还一遍。

更讽刺的是，这些软件往往运行在最要命的场景:电力、医疗、航空、产线。一个反馈缺失导致的误操作，一个信息密度归零导致的漏看报警，代价可能是消费级软件永远无法想象的。越是高风险的领域，越承受不起坏设计，现实却常常正好相反。

专业不是坏设计的许可证。恰恰相反，越专业的工具，越值得被设计好。

# 小结

反馈、连续、信息密度，看似是三件事，内核其实是同一件:**降低用户的认知成本**。反馈消除「我的操作有没有生效」的不确定性，连续消除「这个东西是从哪来的」的困惑，信息密度消除「我该看哪里」的迷茫。好的 UI 不是让用户去理解界面，而是让界面主动把自己解释清楚。
