[2P Game Arcade](https://2pgarcade.com/) 在办一场比赛：把一个完整的游戏装进 1.44MB，也就是一张 3.5 吋高密软盘。规则页在[这里](https://2pgarcade.com/contest-144mb.html)。我自己正在做参赛作品，这篇把规则整理一遍，再讲讲技术上怎么选型才不会一开始就把预算花光。

## 规则

这场比赛致敬的是 1997 年海太（하이텔）网游戏制作社团的百 KB 游戏公募。核心限制只有一条：**全部文件不超过 1,474,560 字节**，包括可执行文件和运行所需的一切。没有"运行时不算"的豁免。

其他要点：

- 必须是独立可执行文件，网页游戏不行；
- 必须是比赛公布后的全新作品；
- 引擎自由，个人或团队均可；
- 允许内部压缩，但解压后仍需符合容量要求。

时间是 2026 年 5 月 23 日起，截止 9 月 4 日晚 11:59，Google 表单提交。评审看三件事：完成度、是否超容量、好不好玩。奖金大奖 72 万韩元、金奖 28 万、银奖 14.4 万，获奖作品会被压进真的软盘做纪念品。

奖金不算多。但"把游戏塞进软盘"这个约束本身比奖金有意思。

## 1.44MB 是什么概念

一张现代游戏的截图就能超过它。一个 Unity 空项目的运行时是它的几十倍。Godot 导出模板也是几十 MB 起步。所以第一条结论很直接：**别用通用引擎**，运行时本身就把预算烧完了。

但 1.44MB 对代码来说其实非常宽裕。代码是全世界压缩比最高的资产——几百 KB 的机器码能装下完整的游戏逻辑、物理、音频合成器和渲染管线。真正吃空间的从来是资产：贴图、音频采样、字体。

所以整个策略可以概括成一句话：**预算花在代码上，资产全部程序化生成**。

## 框架：sokol 或 minifb

引擎不能用，裸写平台层又太费时间，中间这层我推荐两个东西。

**[sokol](https://github.com/floooh/sokol)** 是我在用的。一组单头 C 库，自带 Metal / GL / D3D11 / GLES3 后端，也就是 macOS、Linux、Windows、Android 一套代码全覆盖。链接后的体积开销小到可以忽略，API 是薄薄一层现代图形抽象。Rust 用户有 [sokol-rust](https://github.com/floooh/sokol-rust) 绑定。我的作品用它跑在四个平台上，Android APK 手工用 aapt2 + zipalign + apksigner 打包（不碰 Gradle），最后 650KB 左右，软盘约束连手机版一起守住了。

一个坑：sokol-rust 的 build.rs 按宿主平台而不是编译目标选后端，从 macOS 交叉编译 Windows 会选错。我本地打了补丁按 `TARGET` 选，vendor 进项目就好。

**[minifb](https://github.com/emoon/minifb)** 适合另一种做法：你只想要一个能往里怼像素的窗口，软件渲染，一切自己画。API 十几个函数就学完了，体积同样几乎为零。如果你的游戏是 2D 的、分辨率不高，这条路比 sokol 更简单。

Rust 如果要压缩生成的二进制体积记得加这些：

```toml
strip = true
opt-level = "z"
lto = true
```


## 资产：能算的就别存

我的作品里,音频全部实时合成,没有一个采样文件;弹幕轨迹是混沌动力学吸引子公式,不存路径数据;字形是矢量解码。全项目唯一的大资产是一份 337KB 的位流,装着 GBK 全部汉字的笔画结构——因为游戏玩法就建立在"字会碎成部件"上,这份钱必须花。

这是我想传达的第二条结论：程序化不是妥协，是筛选。什么资产值得占据你六分之一的软盘，这个问题会反过来逼你想清楚游戏到底是关于什么的。1997 年那批百 KB 游戏好玩，不是因为作者们克服了约束，而是约束替他们砍掉了所有装饰性的东西。
