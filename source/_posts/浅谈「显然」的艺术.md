在外行人眼里，似乎代码水平越高，写出来的代码就越"艰深"，即大家都看不懂。但只有时常接触代码的我们才知道，真正高质量的代码，应该是"显然"的。

这里的"显然"不是指数学证明中臭名昭著的"仿照上例显然"，而是指任何（熟悉基本语法）的人在看到代码时都能迅速理解代码含义。

我们先来看一段代码对比，二者功能完全相同：

C Language (这实际不是 C 标准库，是 Windows API，因为 C 标准库没有实现相同功能的函数) 

```c
Sleep(1000);
```

Rust Language

```rust
thread::sleep(Duration::from_secs(1));
```

乍一看你可能有点绷不住：怎么回事？C 这么简洁，怎么 Rust 这么烦？

但是，C 的简洁也是有代价的。比如说光看左边的代码，你能清晰地知道他想要表达什么吗？是进程全部休眠？还是控制小狗睡觉？1000 又是什么意思？是 1000 μs, ns, 分钟, 小时, 还是天？也许你只能查阅 cppreference.com。Sleep 接受的参数是一个 int，意味着你可以传 -2147483648 ~ 2147483647 之间的任何整数。那如果我传了个 -100，那 Sleep 会干什么？把时光倒流吗？相比之下，Rust 这边的意图就十分明确，将当前进程休眠一秒。也许你会说，我还是更喜欢 C 这边，我查过文档了，就是让当前的进程休眠给定的毫秒数。但是，你真的记得住所有的 API（函数调用接口）吗？更严重的是，当你接触到一个新的项目，望着里面成片的 "set_init_mode(114); set_error_level(-1);" 时，你该如何准确地了解每句话的意图？

优秀的代码，文档往往起到的是辅助的作用。

糟糕的代码，想找文档都找不到。

如果你翻网 Win32 早期代码，你可以发现 Win32 的设计者将 WinApi 需要用到的整参数都设为了常量（=2ᵏ），而你则只需用 '|'（按位 OR）将参数连接。如

```c
SetWindowMode(hWindow, KEEP_LEFT | KEEP_TOP);
```

这可以说是很优秀的设计，也是很好的显然。缺点在于，实际上传递的仍是一个 int。所以用户可以轻松地写出 SetWindowMode(hWin, 114514); 而你一点办法也没有。这样的代码也是未定义的。

再来看另外一个例子：查找字符串。

在一个字符串中查找另一个字符串是非常常用的基本操作，以至于 C 与 C++ 都分别将其类置入了标准库中。在 C 语言中，他是：

int strstr(const char* src, const char* dst);

在 C++ 语言中是

(string 内部) unsigned int find(string dst);

很容易猜测 C 语言和 C++ 中返回的整数是 dst 在 src 中出现的位置（第一个）。但是，如果 dst 在 src 中没有出现呢？实际上，C/C++ 采用了"哨兵"来处理情况。例如 strstr 在找不到时返回 -1，而 find 返回 $4294967295 (2^{32} - 1)$，某些平台上是 $2^{64} - 1$。

-1 和 4294967295 就是哨兵值，当遇到这些值时，应当知悉不存在。问题来了：我怎么知道哨兵值是什么？每个函数都可能不一样！（0, nullptr, NULL, false, -1……）答案是只能查阅文档。由此可见，使用哨兵的做法既不优雅，也不显然。

Rust 在设计之初就考虑到了这些问题，用枚举避免了使用任何哨兵，设计上的优势也使它不会再为前文的参数问题烦恼。在用到 时刻 与 时间间隔 时，你无需使用 1970 年 1 月 1 日至今的秒数，也无需用整型代表毫秒，而是使用 Instant 代表时刻，Duration 代表间隔。调用函数传一些 可选项时，也不推荐使用整型，而是写一个结构体处理参数，这样甚至在调用函数之前就可以完成检查。你在编写函数时，就可以确信用户传给的参数是合法的，不用考虑其他情况。

于是就有了 Rust 的 find。
```rust
fn find(&self, dst: &str) -> Option<usize>;
```

`Option<usize>` 是一个枚举，可能有两种取值：None，以及包含值的 Some（一个数）。这样，即使是可判也能猜到用法：找不到时返回 None，找到时返回包含位置的 Some。这样还有一个额外的好处。用户必须显式处理两种情况，不能像直接用返回的 `Option<usize>` 来作为数组索引。如果是 C，用户使用 strstr 若没考虑 -1 的情况，就可能访问到 `a[-1]`，而 `a[-1]` 的访问可能会造成程序直接退出，也可能访问到奇怪的值（总之不属于 a）。

当然，虽然这篇文章以 Rust 标准库为例，但并不意味着只有 Rust 才能贯彻这一原则。你可以在任意语言中使用这一技术，从而让代码清晰可读。

在代码中贯彻了"显然"的艺术后，许多人发现：对于同一个需要解决的问题，两个人的代码总是基本相同的，且不需要花费很长时间思索解决方案，为了使代码质量更高而采用这些原则，结果还收获了编程效率的提升，这不得不说是一种意外之喜了。
